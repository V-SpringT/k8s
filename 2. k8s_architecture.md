#### Question 18: High Availability (HA) `etcd` Quorum & Fault Tolerance
Your team wants to build a Highly Available (HA) Kubernetes cluster using the **Stacked etcd topology** (`kubeadm`). To save hardware costs, a manager proposes deploying **2 Control Plane nodes** (each running an `etcd` member) instead of 3. Why is a 2-node `etcd` cluster actually **less** reliable than a 1-node `etcd` cluster?
* **A.** `etcd` uses the Raft consensus algorithm requiring a strict majority ($\lfloor N/2 \rfloor + 1$) for quorum: for $N=2$, quorum is $2$, meaning if **either** of the 2 nodes fails, the cluster loses quorum and becomes read-only, while doubling the hardware failure surface compared to 1 node.
* **B.** `kube-apiserver` requires an odd number of TCP ports to bind to the Load Balancer.
* **C.** In a 2-node cluster, `kube-scheduler` runs on Node 1 and `kube-controller-manager` runs on Node 2 without replication.
* **D.** Raft requires at least 6 nodes to elect a leader in Stacked etcd mode.
